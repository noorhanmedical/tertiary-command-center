# Phase 1 — Batch Flow handoff contract

**Status:** Docs-only (Batch D4 of Phase 1 run).
**Companion:** `scripts/qa-phase-1-batch-flow-handoff-contract.mjs`.

Pins the upstream flow that produces Engagement-eligible patients.

## Flow

```
Batch Flow
  → Visit vs Outreach derivation
    → Qualification / reasoning generation
      → Admin Review
        → Engagement candidate / handoff
```

## Step 1 — Batch Flow

- **Owner:** Batch Flow ingestion routes (`server/routes/batches.ts`).
- **Output:** `screening_batches` row + `patient_screenings` rows.
- **Canonical ID emitted:** `batchId` + `patientScreeningId`.
- **Audit event:** `patient_journey_events` on batch ingest.
- **Plexus IQ relationship:** Plexus IQ READS batch state for analytics; does NOT mutate it.

## Step 2 — Visit vs Outreach derivation

- **Owner:** Plexus IQ reasoning derivation.
- **Output:** Visit vs Outreach bucket on the screening row.
- **Canonical ID:** `patientScreeningId`.
- **Audit event:** Journey event on commit.
- **Plexus IQ relationship:** Plexus IQ DERIVES the bucket; it is the intelligence layer.

## Step 3 — Qualification / reasoning generation

- **Owner:** Plexus IQ reasoning services (`services/plexusIq/adminReview*`).
- **Output:** `patient_screenings.reasoning` populated.
- **Canonical ID:** `patientScreeningId`.
- **Audit event:** Journey event on reasoning regeneration.
- **Plexus IQ relationship:** Plexus IQ WRITES `reasoning` only; this is its sole operational write target per #182 audit.

## Step 4 — Admin Review

- **Owner:** Admin Review (`routes/admin.ts` + qualification surface).
- **Output:** Approval / commit / reject decision.
- **Canonical ID:** `patientScreeningId`.
- **Audit event:** Journey event on commit/reject.
- **Plexus IQ relationship:** Plexus IQ does NOT decide; Admin Review owns approval.

## Step 5 — Engagement candidate / handoff

- **Owner:** Engagement Center commit (triggered by Admin Review approval).
- **Output:** `patient_execution_cases` row.
- **Canonical ID:** `executionCaseId` minted; `patientScreeningId` linked.
- **Audit event:** Journey event on execution-case creation.
- **Plexus IQ relationship:** Plexus IQ READS execution-case state for aggregation; never writes it.

## Hard rules

- **Batch Flow does NOT own operational call list.** The call list is generated by Engagement Center / scheduler-assignment service AFTER handoff.
- **Plexus IQ does NOT own assignment.** Plexus IQ aggregates assignment state for read-model views; never mints assignments.
- **Admin Review does NOT own call results.** Admin Review approves; the canonical recordCallResult service owns call-result writes.
- **Engagement owns operational workflow after handoff.** Once an execution case exists, Engagement Center owns the lifecycle (engagementStatus, nextActionAt, assignedTeamMemberId).
- **Team Portal consumes assigned work later.** Team Portal sees the call list once scheduler assignments exist for the day.
- **No split-brain.** ONE owner per step. ONE source of truth.

## Plexus IQ posture (re-stated)

Plexus IQ in this flow:
- READS batch / screening / execution-case / engagement / assignment / journey-event / task / triage / billing-readiness / invoice state.
- WRITES only `patient_screenings.reasoning` for qualification reasoning regeneration.
- DERIVES Visit vs Outreach bucket — but the WRITE of the bucket onto the screening row happens via Admin Review approval / commit path.

## Admin Review posture (re-stated)

Admin Review in this flow:
- WRITES approval / commit / reject decision; that decision triggers execution-case creation.
- Does NOT mint operational IDs other than its decision audit event.
- Does NOT write call results, tasks, triage, assignments, ancillaries, billing, invoices.

End of contract.

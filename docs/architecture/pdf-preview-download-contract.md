# PDF preview + download contract

**Status:** Docs-only (Bundle 56). No runtime PDF code touched. No packet generation change. No UI change.
**Date:** 2026-06-10.
**Scope:** Pin how every generated PDF and ancillary document on the platform is previewed, reviewed, downloaded, and audited. Apply to existing PDF families (Plexus packet, clinician packet, ancillary packet, patient packet, billing packet, collection PDF) AND every future generated patient or ancillary document.

This contract ships zero runtime code. Every future PR that touches a preview / download surface MUST cite the §-numbers below in its description.

---

## 1. Applies to

Every PDF and ancillary document generated by the platform:

- **Plexus packets** (Plexus IQ-side patient packet).
- **Clinician packets** (clinician-facing PDF).
- **Ancillary packets** (per-ancillary procedure packet).
- **Order PDFs** (order note generation).
- **Procedure note PDFs**.
- **Report PDFs** (uploaded report wrapping + generated report PDFs).
- **Billing packets** (the billing-document PDF flow).
- **Collection PDFs**.
- **Patient packets** (the multi-patient print-preview packet flows).
- **Future generated patient or ancillary documents** — every new generator inherits the rules below by default.

If a generator is added that bypasses this contract, that is a stop-condition (see §13).

---

## 2. Global rule

**Every generated PDF MUST support preview before download.** No code path may issue a forced download without first rendering a previewable surface the operator can inspect. Forced downloads break the audit trail, hide stale-data risks, and complicate clinician + billing review.

---

## 3. Required flow

```
source data
  → document readiness check
  → generate preview
  → user review
  → download PDF
  → audit event
```

Every PDF surface follows this exact sequence. A future PR that elides any step is non-compliant.

### 3.1 Source data

The data the PDF will render is gathered first. This includes (per PDF family):

- Patient identity (per the role's RBAC envelope — see §10).
- Ancillary / test type.
- Clinical evidence references (per `pdf-protection-contract.md`).
- Order / procedure / report context.
- Billing line context (for billing packets only — money fields stay inside the billing layer per `billing-invoice-hard-stop-map.md`).

### 3.2 Document readiness check

The generator MUST call the readiness evaluator before composing the preview. For PDF families with a readiness counterpart in `billingReadiness.repo.ts:74-118` (informed_consent, screening_form, report, order_note, post_procedure_note), the evaluator returns `ready_to_generate` OR `missing_requirements`. The preview surface MUST honour the evaluator's verdict and surface the `missing` list in the warning area (see §5.6).

### 3.3 Generate preview

The preview is rendered IN-APP, not exported. The user sees the document in a previewable surface (print-preview window, in-app iframe, modal viewer) BEFORE any byte is downloaded.

### 3.4 User review

The user inspects the preview. The download action is NEVER auto-triggered — it requires an explicit click on the Download PDF button.

### 3.5 Download PDF

The downloaded file MUST be byte-identical to the preview the user reviewed (see §4.5). The download fires an audit event (§9).

### 3.6 Audit event

Per §9, every preview, generation, and download writes an audit row.

---

## 4. Required behavior

1. **Generate document data first.** No PDF byte is composed before the source-data + readiness phases complete.
2. **Render PDF preview in the app.** Preview MUST be visible inside the app surface (modal, iframe, browser print-preview window). Headless generation (no preview UI) is forbidden for user-initiated PDF actions.
3. **Allow the user to review the preview before downloading.** No timer, no auto-close, no auto-download.
4. **Provide a clear Download PDF button.** The button is the ONLY path that produces a final file on disk.
5. **Do not force immediate download without preview.** No `window.open(blob, "_self")`, no `<a download>` auto-click on a fresh page, no streaming download from a route that did not first render a preview.
6. **Downloaded PDF must match the previewed version.** Byte-identical OR semantically identical depending on the renderer; the user MUST NOT see a different document than the one they reviewed.
7. **If source data changes after preview, mark preview stale.** A subsequent source-data write (e.g. an admin override, a new uploaded document, a regenerated note) invalidates the open preview.
8. **Stale preview must require regeneration before download.** A stale preview MUST disable the Download PDF button and surface a Regenerate Preview action. The user re-enters §3.3.
9. **Do not generate a final PDF from incomplete/stale data without readiness warnings.** The preview surface MUST warn (banner + missing-list) when the readiness verdict is `missing_requirements` or when the preview is stale.
10. **Preview must show missing document warnings if applicable.** The `missingRequirements` array from the evaluator (Bundle 26 fixture) MUST be rendered in the preview chrome.

---

## 5. Preview surface — required display

The preview surface MUST clearly show:

- **§5.1 Patient identifier** — within the viewer's RBAC scope (see §10). For non-clinical roles the surface MAY render only initials or canonical patient id.
- **§5.2 Ancillary / test type** — e.g. `BrainWave`, `VitalWave`, `Ultrasound`, future ancillaries.
- **§5.3 Document type** — e.g. `clinician_packet`, `plexus_packet`, `billing_packet`, `order_note`, `procedure_note`, `report`, `collection_pdf`.
- **§5.4 Date of service or generated date** — both when both are available.
- **§5.5 Source data used** — a brief enumerator: e.g. "Includes informed consent, order note, post-procedure note, imaging report."
- **§5.6 Readiness status** — `ready_to_generate` | `missing_requirements`, surfaced as a banner.
- **§5.7 Missing-document warnings** — the `missingRequirements` array enumerated; each item linkable to the upstream surface that resolves it.
- **§5.8 Generated status** — `fresh` | `stale`; stale-state disables the Download button per §4.8.
- **§5.9 Stale status if applicable** — surfaced with a Regenerate Preview action.

Any future preview UI MUST render all nine items. A surface that omits one is non-compliant.

## 6. Audit requirements

Every preview, generation, and download MUST produce an audit row carrying:

- **§6.1 Document type**.
- **§6.2 Patient / case reference** — `patientScreeningId` AND `executionCaseId` AND `canonicalPatientId` when each is available.
- **§6.3 Source data version / hash if available** — a deterministic hash over the source-data slice. PDF families that already version their inputs (e.g. `reasoning` blob digest, `case_document_readiness` rows + statuses) MUST include the version pointer; families that don't have one yet are exempt until they do.
- **§6.4 Generated by** — actor user id.
- **§6.5 Generated at** — ISO timestamp.
- **§6.6 Previewed by if available** — actor user id (may differ from generated-by for cross-team review flows).
- **§6.7 Previewed at if available**.
- **§6.8 Downloaded by if available** — actor user id.
- **§6.9 Downloaded at if available**.
- **§6.10 Stale / regenerated status if applicable** — `stale` | `regenerated_from_<previous_audit_id>`.

The audit row uses the existing `patient_journey_events` writer (typed `appendJourneyEvent` per Bundle 12c / PRs #78, #79). The audit event types are:

- `document_preview_generated`.
- `document_preview_regenerated`.
- `document_downloaded`.

`eventSource` is the generator's canonical name (e.g. `clinician_packet_pdf`, `plexus_packet_pdf`, `billing_packet_pdf`, `collection_pdf`, `order_note_pdf`, `procedure_note_pdf`, `report_pdf`).

PHI envelope: per Bundle 8, the audit row is the canonical place patient-identifier data is allowed; non-audit logs MUST NOT carry the same fields.

## 7. Architecture ownership

PDF generation belongs to the **Documents / Reports layer**. Concretely:

- Pure formatting helpers + readiness evaluators live in `server/modules/documents/` (Bundle 27 dormant module).
- Per-family renderers live in `client/src/lib/pdf*` (e.g. `pdfGeneration.ts`, `pdfPacketGrouping.ts`) and any future module that succeeds them.
- The audit + persistence side of the document lifecycle lives in `server/repositories/documentReadiness.repo.ts` and `server/repositories/billingReadiness.repo.ts` for the readiness verdicts; the document body itself never persists outside the documents layer.

### 7.1 Where PDF generation MUST NOT live

PDF generation logic is FORBIDDEN inside these surfaces:

- **Team Tasks** (`server/modules/team-tasks/`) — task layer dispatches, does not render.
- **Operational Queue** (`server/modules/operational-queue/`) — same.
- **Engagement Center** (`server/routes/engagementAssignmentBoard.ts`) — the route may TRIGGER a preview via the existing print-preview helpers, but MUST NOT compose PDF bytes itself.
- **Team Portal UI** (`client/src/components/portal/PortalShell.tsx`, `TeamPortalShell.tsx`) — UI shells dispatch + display; they do not own the renderer.
- **Playground UI** (`client/src/features/command-center/playground/*`, `client/src/components/playground/*`) — Bundle 11 §17 already pins this; the canvas does not embed packet bodies.
- **Billing money / math** (`server/routes/billing.ts`, `server/routes/invoices.ts`, `server/routes/projectedInvoices.ts`, `server/routes/completedBillingPackages.ts`) — money math is its own hard-stop region (Bundle 29). The billing-document PDF is composed by the documents layer; the billing route triggers the preview.
- **Admin Review approval logic** (`server/routes/patients.ts:1048-1201`) — the approval handler appends journey events, it does not produce PDFs.
- **Qualification logic** (`server/services/screening.ts`, `server/services/plexusIq/*`, `server/services/batchAnalysisRunner.ts`) — qualification reads + writes `reasoning` and `qualifyingTests`; the PDF that consumes those fields is rendered downstream.

## 8. Team Portal / Playground roles

Team Portal and Playground are CONSUMERS of the documents layer. They MAY display:

- **`preview_available`** — a packet has been generated and a preview can be opened.
- **`packet_ready`** — the readiness evaluator returned `ready_to_generate`.
- **`missing_documents`** — surface the `missingRequirements` count and (optionally) the linkable items.
- **`needs_order`** — order note required.
- **`needs_procedure_note`** — post-procedure note required.
- **`needs_signature`** — informed consent required.
- **`download_pdf`** — the Download PDF button when the role permits (§10) AND the preview is fresh (§4.6).

Team Portal / Playground MUST NOT:

- Own PDF rendering logic.
- Cache PDF bytes outside the existing documents-layer cache.
- Trigger a download without showing the preview first.
- Hide the readiness banner.
- Render a stale preview's Download button as enabled.

## 9. Ancillary document generation contract

Each of the following has a canonical owner. The owner is the surface where the action FIRES from; the renderer that produces the PDF is always in the documents layer.

- **Order note generation** — fires from the clinician workspace / Admin Review supporting buttons; renderer in documents layer.
- **Procedure note generation** — fires from the procedure-event surface; renderer in documents layer.
- **Report upload** — fires from the portal upload UI; the documents layer stores the bytes and produces a wrapping PDF when one is needed downstream.
- **Report review status** — owned by the documents readiness evaluator (Bundle 26).
- **Required document checklist** — owned by the documents readiness evaluator; surfaces in the Plexus IQ modal, Engagement Center cards, Team Portal panel.
- **Plexus packet** — owned by the documents layer; fires from `PatientPdfActions` + `EngagementAssignmentBoard` + bulk packet flows.
- **Clinician packet** — same owner; fires from the same entry points.
- **Ancillary packet** — same owner; fires per-ancillary.
- **Collection PDF** — owned by the documents layer; fires from the billing route (money math stays in the billing layer; rendering does not).
- **Billing packet** — same as collection PDF.
- **Document readiness** — owned by the documents readiness repo (`server/repositories/documentReadiness.repo.ts`) + Bundle 27 dormant pure helpers.
- **Billing readiness trigger** — owned by `server/repositories/billingReadiness.repo.ts:94+ evaluateBillingReadinessForProcedure`.

## 10. Access / RBAC

Permissions for each action are scoped per the existing RBAC envelope (`team-portal-playground-wiring-contract.md` §21). Concretely:

| Action | Roles that may perform |
|---|---|
| Generate preview | Clinical roles (Patient Care Specialist, Ancillary Care Specialist), Admin, Plexus IQ users (within facility scope). |
| View preview | Same as Generate — additionally: any role with read-access to the underlying patient AND the document family. |
| Regenerate stale preview | Same as Generate. |
| Download PDF (clinical) | Clinical roles, Admin. |
| Download PDF (billing / collection) | Billing roles, Admin. NEVER clinical-only roles by default. |
| View clinical packet (preview) | Clinical roles, Admin. |
| View billing packet (preview) | Billing roles, Admin. |

Cross-tenant access is FORBIDDEN at every level. A user from tenant A cannot preview, download, or even discover the existence of a tenant B document.

A user outside the patient's facility scope receives a 404 (NOT 403) per the Bundle 54 §9 rule, so existence is not revealed.

## 11. Hash + version traceability

Where source data exposes a deterministic version (e.g. `reasoning` blob hash, `documentReadiness.rowsHash`, `evidenceSnapshot.snippetHash`), the audit row carries it in `§6.3`. The downloaded PDF MAY also embed a footer with the source-version pointer so a downstream reviewer can verify the byte-level provenance.

The embedding rule is OPTIONAL today. A future PR that adopts it MUST land its own QA invariant. This contract pins the audit trail; the user-visible embedding is a follow-on decision.

---

## 12. Stale preview — explicit rules

A preview becomes stale when ANY of the following occurs:

- Source data is mutated (any write to the rows that fed §3.1).
- A new document is uploaded to the case (`documentReadiness` row update).
- The readiness verdict flips from `ready_to_generate` to `missing_requirements`.
- A clinician overrides a qualifying factor that the packet references.
- Admin Review approval state changes.

When stale:

- The preview surface MUST render a `stale` badge.
- The Download PDF button MUST be DISABLED.
- A `Regenerate Preview` action MUST be surfaced.
- A `document_preview_regenerated` audit row MUST be written when the user regenerates, including `regenerated_from_<previous_audit_id>` per §6.10.

The downloaded file from a stale preview is forbidden; the only path forward is regeneration.

## 13. Stop conditions for any future PDF PR

A PR touching preview / download / generation MUST stop and ask if:

1. It would issue a download without showing a preview first.
2. It would generate a final PDF from a stale preview.
3. It would skip the readiness check.
4. It would render a preview without showing the readiness banner / missing-list.
5. It would relocate PDF generation logic into Team Tasks, Operational Queue, Engagement Center, Team Portal, Playground, billing money math, or Admin Review approval logic.
6. It would skip the audit row on preview, generation, or download.
7. It would log PHI outside the audit-row envelope.
8. It would change the existing PDF body for any family (`pdf-protection-contract.md` hard-stop applies).
9. It would cross tenants on any read.
10. It would expose billing / collection PDFs to clinical-only roles.
11. It would change document-upload behavior.
12. It would change billing math, claim, remittance, or invoice calculations.
13. It would change Admin Review approval/commit behavior.
14. It would change qualification logic.
15. It would add a migration.

---

## 14. QA gates for any future preview-or-download PR

- `npm run check` clean.
- `npm run build` clean.
- All existing `scripts/qa-*.mjs` pass.
- The PR adds a `scripts/qa-pdf-preview-download-<family>.mjs` script (one per family touched) that asserts:
  - The preview surface renders the §5 items.
  - The Download button is disabled when stale.
  - An audit row is appended with the §6 fields.
  - No PDF rendering logic appears in the forbidden modules from §7.1.
- The PR cites this contract by §-number in its description.

---

## 15. Non-promises

- No specific PDF library is chosen.
- No specific preview UI component is mandated. The contract is on the rule, not the implementation.
- No commitment that all existing PDF surfaces are retrofitted to this contract in a single PR — each family converts independently.
- No commitment to a specific hash algorithm for source-data version pointers.
- No commitment to byte-level embedding of source-version pointers in the PDF body (§11 is optional).
- No change to existing PDF body content.
- No change to existing audit trail shape.

End of contract.

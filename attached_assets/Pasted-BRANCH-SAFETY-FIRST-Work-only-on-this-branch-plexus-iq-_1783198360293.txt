TASK:

Redesign Engagement Center around three simple areas:

1. Assignment Pool
2. Call Results
3. Call Settings

Current problem:
Engagement Center is conceptually confusing. Separate buckets like “Needs Assignment,” “Needs Redistribution,” “Carryover,” and “Assigned Today” are too hard to understand. A patient can be assigned, on a call list, carryover, overdue, or associated with an unavailable team member at the same time.

Goal:
Replace confusing hard-coded assignment buckets with one clear Assignment Pool that tells the patient’s assignment story chronologically. Keep Call Results and Call Settings separate.

Core model:
Engagement Center = Assignment Pool + Call Results + Call Settings.

Architecture rules:
- Admin Review approves patients/tests.
- Approved patients enter Engagement Center Assignment Pool.
- Assignment Pool is the main/default Engagement screen.
- Engagement Center controls assignment, reassignment, distribution, and monitoring.
- Team Member Portal remains where ACS/PCS actually work assigned call lists.
- patient_execution_cases remains the source of truth for current assignment/work state.
- patient_journey_events remains the source of history/timeline.
- Do not automatically assign every approved patient to team members.
- Do not use old Outreach Center.
- Do not use scheduler cards.
- Do not use /api/scheduler-assignments for Engagement-assigned call work.
- Do not use Google Calendar.
- Do not show PDF/document status in Assignment Pool rows.
- Do not change schema unless absolutely required. If schema is required, add a proper migration.

PART 5 — Status Trail

Do not show random flat tag soup.

The Status Trail should tell the patient/case assignment story in chronological order.

Use an arrow/path style.

Examples:

New unassigned patient:
Admin Review Approved → In Assignment Pool → Not Assigned

Assigned patient:
Assigned → On Call List → Active

Assigned patient whose team member is off:
Assigned → On Call List → Team Member Off → Review Assignment

Admin intentionally keeps patient assigned to that person:
Assigned → On Call List → Team Member Off → Kept Assigned to Callista

Carryover patient:
Assigned Yesterday → Not Completed → Carryover Today → Follow-up Needed

Overdue patient:
Assigned → On Call List → Missed Due Time → Overdue

Scheduled patient:
Assigned → Patient Reached → Scheduled

Completed patient:
Assigned → Patient Reached → Scheduled → Completed

Declined patient:
Assigned → Patient Reached → Declined → Cooldown

The Status Trail should be visually primary and easy to read.

PART 7 — Assignment Pool actions

Each row should have clear actions depending on state.

Common actions:
- Assign
- Reassign
- Return to Pool
- Hold / Pause
- Open Patient
- View History

Special action:
If patient is assigned to a team member who is off/unavailable, show:

Keep assigned to [Team Member Name]

Examples:
- Keep assigned to Callista
- Keep assigned to Ashraful
- Keep assigned to Marge

Behavior:
- patient remains assigned to the same team member
- patient remains on that team member’s call list
- patient is not redistributed automatically
- status trail updates to:
  Assigned → On Call List → Team Member Off → Kept Assigned to [Team Member Name]
- record an event in patient_journey_events if existing event infrastructure supports it
- admin can still later reassign if needed

Important:

PART 10 — Assignment Pool data derivation

Derive state from real data.

Use patient_execution_cases and patient_journey_events.

Suggested logic:
- no assignedTeamMemberId → Not Assigned
- assignedTeamMemberId exists → Assigned
- assigned case visible in Team Member Portal call list → On Call List
- assigned team member off/unavailable if platform data supports it → Team Member Off
- admin chose keep assigned → Kept Assigned to [name]
- incomplete prior-day assigned case → Carryover Today
- nextActionAt before now and still active → Overdue
- call result indicates scheduled → Scheduled
- call result indicates declined → Declined
- cooldown active if existing data supports it → Cooldown

If a piece of data is not available, do not fake it.
Show an honest fallback or omit that part of the trail.

PART 12 — Call Settings tab

- scheduled-patient target

- carryover
- remaining new capacity
- active/inactive

Formula:
remaining new capacity = daily completed-call target - incomplete carryover

Example:
Callista target: 30
Carryover: 12
New allowed today: 18

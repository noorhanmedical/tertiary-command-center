TASK:

Make Patient Directory sections configurable by admin.

Current need:
Patient Directory is becoming a true EMR-style chart with many sections:

- Demographics
- Ancillary Overview
- Cooldown Eligibility
- Qualifying Tests
- Diagnoses
- Insurance & Eligibility
- Providers
- Medications
- Allergies
- Labs
- Imaging
- Vitals
- Encounters / Notes
- Calls & Comms
- Scheduling
- Documents
- Billing / Readiness
- Ad Automation

Admin needs the ability to allow or restrict which sections appear for different user roles or portal types.

Goal:
Create admin-configurable Patient Directory section visibility and access rules.

Architecture rules:
- Patient Directory remains the canonical patient profile/chart area.
- Do not remove sections from the codebase.
- Do not hard-delete any patient data.
- This is visibility/access configuration only.
- Use real role/session information.
- Do not expose restricted sections to unauthorized users.
- Do not create fake patient data.
- Do not break Team Member Portal deep links.
- Do not break Patient Directory direct route.
- Do not break admin access.
- Do not change schema unless absolutely required.
- If schema is required, add a proper migration.

PART 5 — Apply configuration to Patient Directory left nav

The Patient Directory left navigation should only show sections allowed for the current user.

Rules:
- If section is hidden, do not show it in the left nav.
- If section is summary-only, show it but render only summary content.
- If user tries to deep-link to a hidden section, show an access denied / section unavailable state.
- Do not silently show restricted content.
- Admin should be able to preview by role if existing admin preview pattern supports it.

PART 6 — Apply configuration to section content

Do not rely only on hiding nav items.

Protect the actual content render.

Examples:

If user is not allowed to see Labs:
- Labs nav item should not show.
- Direct URL/deep-link should not render lab data.
- Show: “This section is not available for your role.”

If user is allowed summary-only:
- Show only summary card.
- Hide detailed table/results.

If user has full access:
- Show full section.

PART 7 — Backend safety if needed

If Patient Directory sections are backed by separate endpoints and sensitive data is fetched independently:

- protect backend endpoints with role checks where practical
- do not fetch restricted heavy sections for unauthorized users
- avoid fetching hidden labs/imaging/medications for roles that cannot view them

At minimum:
- frontend must not render restricted sections
- backend should not return sensitive details to unauthorized users if existing route structure allows control

Do not broad-refactor backend routes unless required.

PART 8 — Persistence

Admin configuration must persist.

Use existing settings/config infrastructure if available.

- add a narrow additive table or config entry for patient_directory_section_access
- include a migration
- do not use localStorage for production-critical access settings

Suggested data shape:

- role
- sectionId
- accessLevel: hidden | summary | full
- visible
- updatedBy
- updatedAt

Settings must survive refresh.

PART 9 — Defaults and fallback

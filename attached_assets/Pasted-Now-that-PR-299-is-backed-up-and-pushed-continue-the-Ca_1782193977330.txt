ARCHITECTURE PRINCIPLE
============================================================

Use this model:

patient_execution_cases = canonical operational case / assignment truth

scheduler_assignments = live call-list work item / scheduler visibility queue

call attempts/history = immutable interaction history if table exists

admin audit view = shows whether the bridge is healthy

The flow should be:

Engagement assignment command
→ CallListEngine / CaseAssignmentService
→ updates patient_execution_cases
→ upserts scheduler_assignments
→ records audit or bridge event if available
→ recalculates next_action_at
→ returns call-list visibility status

Team Portal read endpoint
→ resolves logged-in user to scheduler/team-member identity
→ reads active scheduler_assignments
→ joins patient_execution_cases/patient data
→ returns visible call-list rows

Call result command
→ updates scheduler_assignments
→ updates patient_execution_cases
→ appends call attempt/history if available
→ recalculates next_action_at
→ routes to scheduler/admin review/follow-up as needed

============================================================
STEP 5 — NEXT_ACTION_AT POLICY
============================================================

Create one function:

calculateNextActionAt(input)

Rules:
- On assignment with no callback time: now or current queue time.
- Callback Requested: callback datetime required.
- No Answer / Voicemail: retry policy or existing repo policy.
- Wrong Number: no next_action_at unless alternate number exists.
- Declined: null and inactive.
- Scheduled: null or appointment datetime based on current scheduler convention.
- Needs Admin Review: null for normal call list and route to admin review.
- Completed: null.

Do not leave active assigned cases with NULL next_action_at unless intentionally documented.

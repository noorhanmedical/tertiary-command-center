==================================================
CANONICAL DATA FLOW
==================================================

Build the portal around this existing flow:

 patient_screenings / qualification
   ↓
 patient_execution_cases / ancillary workflows
   ↓
 global_schedule_events / procedure events
   ↓
 generated_notes / documents / ancillary reports
   ↓
 physician signature status
   ↓
 document_readiness / billing_readiness
   ↓
 billing_documents / completed_billing_packages
   ↓
 invoices / invoice_batches / financial_events / remittance if present
   ↓
 Physician Portal metrics + financial health

The portal should not be the source of truth.
It should read from and write back into the canonical workflow.

==================================================
SOURCE-OF-TRUTH RULES
==================================================

1. Screening / qualification source of truth

Use existing patient screening/qualification data for:
 - patients screened
 - patients qualified
 - diagnoses/qualifying conditions
 - ancillary eligibility
 - qualification status

Do not calculate screened/qualified counts from documents alone.

2. Execution case / ancillary workflow source of truth

Use execution cases and/or schedule/procedure-event data for:
 - ancillary type
 - scheduled ancillary tests
 - completed tests
 - patient/test chain
 - service type
 - date of service

3. Ancillary Documents layer

Ancillary documents are a workflow layer, not the whole source of truth.

They should connect:

 patientScreeningId / executionCaseId
   → serviceType / ancillary type
   → order note / procedure note / post-procedure note
   → report/result upload
   → signature status
   → billing readiness

Generated notes/documents should power the signing queue only when linked back to the patient/test/execution case.

4. Signature source of truth

Use existing generated notes/document readiness if they already support status tracking.

If not, add minimal canonical signature tracking.

Do not create a disconnected signature table that cannot update billing readiness.

Required signature relationships:
 - documentId or generatedNoteId
 - patientScreeningId
 - executionCaseId if available
 - facility/clinic
 - clinician/physician user id
 - document type: order, procedure note, post-procedure note
 - service type: BrainWave, VitalWave, Ultrasound, PGx, etc.
 - status: needs_signature, ready_to_sign, signed, returned_for_correction
 - signed timestamp
 - signed by user id
 - audit entry

If a new table is needed, possible concept:

 physician_signature_items
   id
   patientScreeningId
   executionCaseId
   facilityId
   clinicianUserId
   documentId or generatedNoteId
   documentType
   serviceType
   status: needs_signature | ready_to_sign | signed | returned_for_correction | voided
   signable: boolean
   blockReason
   signedAt
   signedByUserId
   returnedAt
   returnedByUserId
   returnReason
   createdAt
   updatedAt

But only add this if necessary. Prefer extending existing generated notes/document readiness if cleaner.

5. Billing readiness source of truth

Billing readiness should tell Financial Health what is blocked and why.

Examples:
 - missing signature
 - missing order
 - missing procedure note
 - missing report/result
 - missing billing document
 - missing insurance/eligibility
 - ready to bill
 - submitted
 - paid
 - denied

6. Financial Health source of truth

Financial Health must be driven from billing/financial data, not estimated from appointment counts alone.

Use available data in this order:
1. remittance/payment/denial/ERA/EOB/claim status data if present
2. invoice financial events
3. invoice batches / submitted invoices
4. completed billing packages
5. billing documents and billing readiness
6. projected/estimated values only where actual payment data does not exist

Always separate:
 - actual paid/remitted money
 - submitted but unpaid
 - pending AR
 - denied/rejected
 - billing-ready but not submitted
 - estimated/projected revenue

7. Plexus ancillary contribution

Financial Health should show:

 Overall Clinic Financial Health
   └─ Plexus Ancillary Contribution

Do not make Financial Health only an ancillary dashboard.

 - confirmation required

 - user id
 - timestamp
 - document/generated note id

 - executionCaseId if available
 - action: signed, bulk_signed, returned_for_correction
 - return reason if applicable
 - IP/session metadata if existing audit system supports it

Signature write behavior:
 - update signature status
 - update signedAt/signedBy
 - remove item from Needs Signature

 - preserve audit trail
